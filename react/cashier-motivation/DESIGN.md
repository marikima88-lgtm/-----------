# Раздел «Мотивация кассиров» — дизайн-документ

Порядок в этом документе соответствует ТЗ: 1) схема БД, 2) формулы, 3) примеры расчёта,
4) структура интерфейса. Реализация (код) и тесты — в соседних файлах этой папки.

## ⚠️ Расхождение в исходном примере ТЗ

В примере «3-й месяц» указано «номера: 251». При базовом нормативе 359 и коэффициенте адаптации 70%:
`359 × 0.7 = 251.3`. Правило округления в ТЗ — «в большую сторону» (`ceil`), значит корректное
значение — **252**, а не 251. Похоже на опечатку в исходном примере. В коде и во всех расчётах
ниже применено буквальное правило округления вверх, то есть **252**. Если фактически нужно
округление «до ближайшего целого» (`round`), то и 107.7→108 тоже надо будет пересчитать — с `round`
получится то же 108, а 251.3 → 251. Итог: `round` даёт числа из примера ТЗ ровно, кроме этого не
влияет на остальные примеры. Способ округления вынесен в настройки (`roundingMode`), поэтому это
переключается одной настройкой без правки кода — по умолчанию поставлен `ceil`, как написано
текстом правила.

## 1. Структура базы данных

### `departments` — отделения
| поле | тип | описание |
|---|---|---|
| id | uuid/serial PK | |

### `employees` — кассиры

|---|---|---|

| status | enum('active','terminated') | |
| created_at / updated_at | timestamp | |

### `employee_department_history` — история переводов между отделениями
| поле | тип | описание |
|---|---|---|
| id | PK | |
| employee_id | FK → employees | |
| department_id | FK → departments | |
| date_from | date | |
| date_to | date, nullable | `null` = текущее отделение |

Хранится, чтобы при переводе сотрудника показатели за прошлые месяцы оставались привязаны к
отделению, где они были фактически достигнуты (п. 11 ТЗ). `monthly_facts.department_id` ниже
фиксирует это на уровне факта, история нужна для отчётов «по отделению за период».

### `monthly_facts` — фактические показатели за месяц (источник истины)
| поле | тип | описание |
|---|---|---|
| id | PK | |
| employee_id | FK → employees | |
| department_id | FK → departments | отделение **на момент этого отчётного месяца** |
| year | int | |
| month | int (1–12) | |
| operations | int | факт по операциям |
| phone_numbers | int | факт по собранным номерам |
| reviews | int | факт по отзывам |
| absence_days | int, default 0 | дни отпуска/больничного в этом месяце |
| has_data | boolean | `false` → показатель «Нет данных», не приравнивается к 0 |
| created_at / updated_at | timestamp | |

Уникальный индекс: `(employee_id, year, month)`.

### `motivation_settings` — настройки (singleton-таблица или key/value)
| поле | тип | описание |
|---|---|---|
| id | PK, всегда 1 запись (или key/value пары) | |
| base_norm_operations | int | 1200 |
| base_norm_phone_numbers | int | 359 |
| base_norm_reviews | int | 15 |
| adaptation_month1 / 2 / 3 / from_month4 | decimal(5,4) | 0.30 / 0.50 / 0.70 / 1.00 |
| weight_operations / phone_numbers / reviews | decimal | по умолчанию равные (33.33% каждый) |
| rating_a_min | decimal | 100 |
| rating_b_min | decimal | 80 |
| min_metric_threshold | decimal | 50 — порог «капа» рейтинга |
| rounding_mode | enum('ceil','round','floor') | ceil |
| partial_month_method | enum('calendarDays','workDays') | calendarDays |
| updated_at, updated_by | | аудит изменений настроек |

Хранить как **историю версий настроек** (не перезаписывать поверх), чтобы расчёты за прошлые
месяцы не «переезжали» задним числом при изменении норматива админом. В демо-версии (без бэкенда)
это упрощено до одного текущего объекта настроек в памяти — см. раздел «Ограничения демо».

### Производные данные — `monthly_results` (не обязательная таблица)
Результат расчёта (индивидуальный норматив, % выполнения, рейтинг) — **чистая функция** от
`monthly_facts` + `employees.hire_date` + `motivation_settings`, поэтому её можно как считать на
лету, так и материализовать в таблицу `monthly_results` для скорости отчётов на больших объёмах.
Рекомендация: считать на лету на бэкенде/в API-слое, кэшировать по необходимости — единый источник
формул тогда один (`calc/engine.ts` в этом проекте), а не два синхронизируемых места.

## 2. Формулы расчёта

### 2.1 Коэффициент адаптации по месяцу работы
```
adaptationFactor(monthsWorked) =
  monthsWorked <= 1 → settings.adaptation.month1       (0.30)
  monthsWorked == 2 → settings.adaptation.month2        (0.50)
  monthsWorked == 3 → settings.adaptation.month3        (0.70)
  monthsWorked >= 4 → settings.adaptation.fromMonth4     (1.00)
```

### 2.2 Индивидуальный норматив по показателю
```
individualNorm = round_up( baseNorm × adaptationFactor × prorationFactor )
```
`prorationFactor` = 1, если месяц отработан полностью. Если сотрудник устроился в середине месяца
или был в отпуске/на больничном — `prorationFactor = отработанныеДни / всегоДнейВПериоде`
(календарные или рабочие дни — переключается настройкой `partialMonthMethod`).

### 2.3 Процент выполнения по показателю
```
percent = fact / individualNorm × 100%
```
Не ограничивается сверху (перевыполнение видно как есть, например 130%). Если `individualNorm = 0`
(не должно происходить при корректных настройках, но защищаемся) — показатель помечается «нет
данных», а не делится на ноль.

### 2.4 Общий процент выполнения
```
overallPercent = Σ(percent_i × weight_i) / Σ(weight_i)
```
Веса не обязаны суммироваться ровно в 100% — формула нормализует сама. По умолчанию все три веса
равны (33.33% / 33.33% / 33.33%).

### 2.5 Буквенный рейтинг
```
base =
  overallPercent >= ratingThresholds.aMin → 'A'   (100%)
  overallPercent >= ratingThresholds.bMin → 'B'   (80%)
  иначе                                    → 'C'

если min(percent_operations, percent_phoneNumbers, percent_reviews) < minMetricThreshold (50%):
    рейтинг = 'C'   (даже если base был 'A' или 'B')
иначе:
    рейтинг = base
```

### 2.6 Динамика к прошлому месяцу
```
dynamics = overallPercent(текущий месяц) − overallPercent(прошлый месяц)
```
Если данных за прошлый месяц нет — статус «нет данных для сравнения», а не 0.

### 2.7 Особые случаи, влияющие на формулы
- **Нет `hire_date`** → сотрудник считается действующим, применяется норматив «с 4-го месяца»
  (100%), в интерфейсе — предупреждение «Не указана дата начала работы».
- **Нет данных за месяц** (`has_data = false`) → строка показывает статус «Нет данных», рейтинг не
  считается (не приравнивается автоматически к C).
- **Перевод между отделениями** → берётся `department_id` из конкретной записи `monthly_facts`,
  а не текущее отделение сотрудника — так исторические месяцы не переезжают в новое отделение.

## 3. Примеры расчёта

### Пример A — новый кассир, 1-й месяц, устроился в середине месяца
- Дата начала: 15 июня. Отчётный месяц: июнь (30 дней).
- `monthsWorked = 1` → `adaptationFactor = 0.30`.
- Базовые (без пропорции): операции 360, номера 108, отзывы 5 (округление вверх).
- Пропорция по календарным дням: отработано 16 дней из 30 → `prorationFactor = 16/30 = 0.5333`.
- Индивидуальные нормативы: операции `360×0.5333=192`, номера `108×0.5333=57.6→58`,
  отзывы `5×0.5333=2.67→3`.
- Факт: операции 210, номера 60, отзывы 3.
- % выполнения: операции `210/192=109.4%`, номера `60/58=103.4%`, отзывы `3/3=100%`.
- Общий % = `(109.4+103.4+100)/3 = 104.27%`.
- Все показатели ≥ 50% → капа нет. `104.27% ≥ 100%` → **рейтинг A**.

### Пример B — действующий кассир, 5-й месяц, полный месяц
- `monthsWorked = 5` → `adaptationFactor = 1.00`, пропорция 1 (полный месяц).
- Нормативы: операции 1200, номера 359, отзывы 15.
- Факт: операции 900, номера 300, отзывы 10.
- % выполнения: `75%`, `83.56%`, `66.67%`.
- Общий % = `(75+83.56+66.67)/3 = 75.07%` → база `C` (< 80%). Капа не нужна, база уже C.
- **Рейтинг C**.

### Пример C — правило «капа» по минимальному показателю
- Действующий кассир, месяц 4+, нормативы стандартные.
- Факт: операции 1400 (117%), номера 400 (111%), отзывы 6 (**40%**).
- Общий % = `(117+111+40)/3 = 89.33%` → база `B` (80–99.99%).
- Но `min(117, 111, 40) = 40% < 50%` → капа срабатывает.
- **Итоговый рейтинг: C**, несмотря на общий % 89.33%.

### Пример D — отпуск в течение месяца
- Действующий кассир (месяц 6), 8 дней отпуска в отчётном месяце (30 дней).
- `prorationFactor = (30-8)/30 = 0.733`.
- Норматив операций: `1200×0.733=880`. Аналогично для остальных.
- Дальше расчёт процента и рейтинга идёт по тем же формулам от уменьшенного норматива.

## 4. Структура интерфейса

### 4.1 Страница «Мотивация кассиров» (`MotivationPage`)
1. **Сводная статистика по отделению** (верх страницы): кол-во кассиров, кол-во A/B/C, средний %
   выполнения, лучший кассир месяца, кто просел к прошлому месяцу, кто не выполнил норматив.
2. **Панель фильтров**: месяц, год, отделение, кассир, статус (новый/действующий), рейтинг A/B/C.
3. **Таблица кассиров**: ФИО (кликабельно → карточка), отделение, месяц работы, факт/норматив/%
   по каждому из 3 показателей с цветовым индикатором (🟢 ≥100%, 🟡 80–99.99%, 🔴 <100%... точнее
   <80%, зона 80–99.99% жёлтая), общий %, рейтинг, динамика (стрелка + число).
4. Кнопка **«Экспорт в Excel»**.
5. Вкладка/ссылка на **«Настройки нормативов»** (админ-панель).

### 4.2 Карточка кассира (`CashierCard`, drawer/dialog по клику на ФИО)
- Шапка: ФИО, отделение, дата начала работы, текущий месяц адаптации (или «действующий»).
- Блок действующих нормативов (с учётом адаптации/пропорции текущего месяца).
- Факт / % выполнения / итоговый рейтинг за отчётный месяц.
- 5 отдельных графиков за 6 или 12 месяцев (переключатель периода):
  1. Операции: факт vs норматив по месяцам.
  2. Номера: факт vs норматив по месяцам.
  3. Отзывы: факт vs норматив по месяцам.
  4. Общий % выполнения по месяцам.
  5. Рейтинг по месяцам (A/B/C как ступенчатая шкала).
- Норматив на графике показан отдельной линией **именно тем, каким он был в конкретном месяце**
  (у нового сотрудника он растёт от месяца к месяцу — это ключевая причина показывать факт и
  норматив вместе, а не единую плоскую линию).

### 4.3 Настройки администратора (`AdminSettingsPanel`)
Форма (react-hook-form) со всеми полями `motivation_settings`: 3 базовых норматива, 4 процента
адаптации, 3 веса показателей, 2 границы рейтинга, порог капа, режим округления, метод расчёта
неполного месяца. Сохранение обновляет объект настроек в контексте (в демо — только в памяти,
на бэкенде — новую версию настроек с датой начала действия).

### 4.4 Экспорт в Excel — 7 листов
«Сводка по кассирам», «Динамика по месяцам», «Рейтинг A», «Рейтинг B», «Рейтинг C», «Невыполненные
нормативы», «Настройки нормативов» — в каждой строке сотрудника: ФИО, отделение, отчётный месяц,
месяц работы, факты, нормативы, %, общий результат, рейтинг, изменение к прошлому месяцу.

## Ограничения демо-версии

Как и в разделе «Кассовые ордера», это набор React-компонентов без сборки и без бэкенда:
- Данные (`employees`, `monthlyFacts`, `settings`) живут в React Context в памяти — изменения в
  настройках или пометки «уволен»/перевод отделения не переживают перезагрузку страницы.
- Формулы реализованы как чистые функции в `calc/engine.ts` — именно они тестируются в
  `calc/engine.test.ts` (Vitest) и именно их нужно перенести на бэкенд как единственный источник
  правды при подключении реальной БД, чтобы фронт и бэк не считали рейтинг по-разному.
